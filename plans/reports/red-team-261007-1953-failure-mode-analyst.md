# Red team: failure-mode analysis of the Ollama context-fit plan

Plan: `plans/261007-1948-ollama-context-fit/` (plan.md, phases 1-5). Perspective: failure mode analyst plus flow tracer. The locked user decisions (patch 0005, full load-and-search, the three triggers) are not challenged. Only how the plan implements them is.

## Finding 1: The scheduler, its streaming gate and the restart fan-out only cover the window they run in
- **Severity:** Critical
- **Location:** Phase 4, section "Scheduler" ("owned by the main window … only one instance runs", "restart every idle tab's sidecar"). Phase 3, section "Applying a change".
- **Flaw:** Neither shell has a "main window". Every window is a peer with its own renderer stores. The restart IPC the plan reuses picks its sidecar from the calling window.
- **Failure scenario:** The user has two windows: window A is idle and window B is streaming a reply on gemma E4B. A's scheduler sees "no tab streaming" because it reads only its own stores, starts the stale or pulled measurement, and loads E4B at 8k, 16k and so on. B's in-flight `/api/chat` is either evicted mid-generation or forced to reload. When the new value lands, A's fan-out restarts A's tabs only. B's tabs keep the old `PI_OLLAMA_CONTEXT_LIMITS` until their next crash or manual restart, so acceptance criterion 4 fails for them without any error. If every window mounts the scheduler instead, N schedulers race. Main's single-flight rejects all but one with `busy`, and each window shows its own error or retries.
- **Evidence:** `src/main/window.ts:136` (`createWindow`, called from `src/main/index.ts:302,327`) and the "New Window" menu (`src/main/menu-template.ts:72-74`). Tauri has `session:open-new-window` (`src-tauri/src/services/mod.rs:77`). The restart is scoped to one window: `src/main/ipc.ts:861-868` (`BrowserWindow.fromWebContents(event.sender)` → `sidecarPool.sidecarForTab(win, …)`) and `src-tauri/src/tabs/ipc.rs:398-405` (`ctx.tabs.sidecar_for_tab(caller.win_id, …)`).
- **Suggested fix:** Put the queue, the "any sidecar busy" gate and the restart fan-out in main/Rust, where `sidecarPool` / `ctx.tabs` see every sidecar. Broadcast `ollama:context-changed` to every window. Each renderer then restarts its own tabs, or main restarts idle sidecars directly with each tab's session path.

## Finding 2: Nothing stops a chat turn from starting after a measurement has begun, and a corrupted result is stored as truth
- **Severity:** Critical
- **Location:** Phase 4, "Scheduler" ("runs the next item only when no tab is streaming"). Phase 2, "Algorithm" (`fits(n)` reads `/api/ps` "entry for tag", and checks `context_length == n` only "when the field is present").
- **Flaw:** The plan checks for streaming once, when an item starts. A load-and-search run takes several loads, each with up to 120 s timeout. Disabling the Measure button while a tab streams is the reverse direction: nothing disables the composer while a measurement runs. The startup stale check fires right when users send their first message.
- **Failure scenario A (same model):** The scheduler measures E4B. Mid-search the user sends a prompt on E4B. The sidecar's `/api/chat` carries `num_ctx = 131072`, so Ollama reloads the runner at 131072. The next probe's `/api/ps` reads that runner. On Ollama builds without `context_length` the plan's guard is skipped, so the probe records the chat's `size`/`size_vram` under the wrong `n`. The user's reply also stalls behind two forced reloads.
- **Failure scenario B (different model):** The user chats on model X while model Y is measured. Both runners compete for VRAM, Y's `size_vram < size` at a rung that fits on its own, and the binary search drops the top half. The low maximum is persisted. Nothing re-measures it: the fingerprint is unchanged, and the plan triggers only on pull, hardware change or a manual press. The user's cap is silently clamped down to it (Phase 3 `context-measure` "drops" a cap above the new max).
- **Evidence:** In `patches/omp/0001-ollama-native-api-num-ctx.patch`, `createChatBody` sends `num_ctx` on every request. Discovery runs in every sidecar. The research showed that `/api/ps` sizes track `num_ctx` exactly (`plans/reports/research-261007-1853-ollama-context-from-machine-spec.md:11-19`), so any foreign load shifts them.
- **Suggested fix:** While a measurement runs, either hold new prompts or abort the measurement as soon as any sidecar receives one; main can hook the `prompt` RPC passthrough to do this. Discard a probe when `/api/ps` lists any other runner, or when `context_length` is absent or differs from `n`. In that case retry instead of recording "does not fit".

## Finding 3: Choosing the pool from the host's hardware probe misclassifies AMD and Intel GPUs, GPU-less Ollama and nvidia-smi timeouts, and makes the fingerprint flap
- **Severity:** High
- **Location:** Phase 2, "Algorithm" (`pool = machine.vramBytes > 0 && !unifiedMemory ? "gpu" : "ram"`). Phase 3, "Store shape" (`isStale` field-wise, including `gpuName`).
- **Flaw:** `vramBytes` comes only from `nvidia-smi`, which has a 2 s timeout. Otherwise it is null, and `gpuName` then comes from a different source: Chromium GPU info on Electron, `lspci`/sysfs on Tauri. The pool describes the GUI host, not what Ollama actually uses.
- **Failure scenarios:**
  1. On an AMD (ROCm) or Intel GPU, `vramBytes` is null, so the pool is `ram` and the test is `size <= ramBudget`. A context that spills half the layers from the GPU to the CPU passes, which breaks the plan's promised outcome ("never CPU spill").
  2. With NVIDIA present but Ollama running without the GPU (Docker without `--gpus`, or a driver/CUDA mismatch), the pool is `gpu` and `size_vram` is 0 at every rung. Every model gets the floor (see finding 4), even though RAM would allow far more.
  3. When `nvidia-smi` is slow at boot (persistence mode off, which often takes more than 2 s), `vramBytes` is null and `gpuName` switches to the lspci or Chromium string. `isStale` reports a hardware change, every model is re-measured in the `ram` pool and gets a RAM-sized maximum that spills on the GPU. On the next boot `nvidia-smi` answers, the fingerprint flips back, and everything is re-measured again. Each startup evicts models and restarts tabs.
- **Evidence:** `src/main/ollama/hardware.ts:9` (`HARDWARE_PROBE_TIMEOUT_MS = 2_000`), `:120-127` (NVIDIA-only VRAM, fallback `vramBytes: null, gpuName: gpuNameFromInfo(info)`). `src-tauri/src/ollama/hardware.rs:72-84,127-128` (lspci/sysfs name source). The research leaves this open: "Ollama's response for a CPU-only or AMD setup was not tested here" (research report, "Unresolved questions").
- **Suggested fix:** Take the pool from Ollama itself. Load the floor rung: when `size_vram > 0`, use the GPU test; when it is 0, use the RAM budget. Build the fingerprint only from fields that came from a successful probe, and treat a failed probe as "unknown", never as "changed".

## Finding 4: Every probe failure collapses to an 8k floor, below what the agent needs, with no fallback to today's value
- **Severity:** High
- **Location:** Phase 2, "Algorithm" ("when even the floor does not fit → max = floor", ladder starts at 8192). Phase 3, `clampCap` ("an integer in `[ladder floor, maxContext]`").
- **Flaw:** The design treats "does not fit" as a measurement. In practice it is also how systematic misreads show up: `size_vram` missing on an older Ollama (`undefined >= size` is false), `context_length` reporting `num_ctx × OLLAMA_NUM_PARALLEL`, finding 3's GPU-less daemon, or finding 2's contention. Each one writes `maxContext = 8192`, and it is then sent as `num_ctx`. Patch 0001 exists because a context below the agent's first request fails the first turn. Its default floor is 16384, and the research says "16384 stays the floor". The plan lowers the floor to 8192 and lets the user pick it.
- **Failure scenario:** A user on an Ollama version whose `/api/ps` lacks `size_vram` updates the app. The startup stale check measures every model, all of them land at 8192 / "spills", and every session's first turn overflows or is silently truncated. Before this change they had 131072. Nothing in the rollback section covers recovering from bad stored data.
- **Evidence:** `patches/omp/0001-ollama-native-api-num-ctx.patch` (`OLLAMA_NATIVE_DEFAULT_CONTEXT = 16_384`, "Ollama's own default (4096 on most GPUs) is smaller than the agent's first request"). Monorepo `packages/coding-agent/src/config/model-discovery.ts:163`. Research report line 60 ("16384 stays the floor"). `src/main/sidecar.ts:381` (today's value is 131072).
- **Suggested fix:** Make the floor 16384. Treat "required field missing" or "`context_length` ≠ n" as `error` (no entry written, so the sidecar keeps the 131072 fallback), not as `spills`. Never persist a floor verdict unless the floor rung's `/api/ps` row is complete and is the only runner.

## Finding 5: The binary search assumes clean, monotonic probes that Ollama reloads do not give it, and a one-off misread becomes permanent
- **Severity:** High
- **Location:** Phase 2, "Algorithm" ("monotonic in n: same result as walking every rung", "Ollama reloads the runner when `num_ctx` changes, so no explicit unload is needed between probes").
- **Flaw:** Each probe reloads in place. Ollama sizes against free VRAM at load time (the plan's own Risks section says so). Right after the previous runner exits, the driver may not have released its memory yet. A lower rung can then spill while a higher rung tried earlier fit, so the probes are noisy and not monotonic. Binary search turns one noisy probe into the loss of every rung above it. The fake Ollama in phase 2 is deterministic (weights + kv × n against a fixed limit), so no test can exercise this.
- **Failure scenario:** On the 16 GiB card from the research (6.8 GiB already used by other processes), the search probes 64k (fits), then 128k. The 64k runner's memory has not been freed yet, so 128k spills and the result is 64k. The stored value stays there until the hardware changes. The research loaded only three rungs, all of them fitting, and never saw a spill or a reload-after-spill sequence (research report:11-19).
- **Suggested fix:** Before each probe, unload explicitly (`keep_alive: 0`) and poll `/api/ps` until the tag is gone. Confirm the winning rung with a second load. Record `freeVramAtMeasure` with the probes, so the UI can show "measured with X GiB free" and the user knows when Measure again helps. Add a fake-Ollama fixture that has free-VRAM lag.

## Finding 6: "Restart on `agent_end`" is not "idle", and the fan-out restarts tabs whose model did not change, once per measured model
- **Severity:** High
- **Location:** Phase 4, "Scheduler" ("restart every idle tab's sidecar … For a streaming tab, defer the restart to its `agent_end`"). Phase 3, "Applying a change".
- **Flaw:**
  1. The existing restart path refuses while `isStreaming || isCompacting`. The plan only checks streaming. In omp, auto-compaction and other post-turn maintenance run inside the `agent_end` handler, and the wire `agent_end` is deferred around in-flight prompts. A restart keyed on `agent_end` can therefore kill a compaction, a retry or a queued follow-up (`queuedMessageCount`).
  2. Every effective-value change emits `context-changed`, which restarts every idle tab, including tabs on other models. The startup stale pass measures K models one after another, which means K full restart rounds. Each restart re-resolves the shell env, which can take up to 4 s. A user who submits a prompt during that window races a SIGTERM.
- **Evidence:** `src/renderer/lib/command-registry.ts:222-232` (the guard checks `isStreaming || isCompacting`). Monorepo `packages/coding-agent/src/session/agent-session.ts:3137-3139` (deferred wire `agent_end`), `:3216-3229`, `:3956-3960` (auto-retry and compaction run in the `agent_end` handler), `:4277-4278` (`checkCompaction` after the turn). `src/renderer/stores/session.ts:34,54` (`isCompacting`, `queuedMessageCount`). `src/main/sidecar.ts:331` (env resolution takes up to 4 s), `:697-702` (`restart` kills before it respawns).
- **Suggested fix:** Restart only tabs whose current model's effective limit changed. Wait for `!isStreaming && !isCompacting && queuedMessageCount === 0`. Debounce the fan-out until the scheduler queue is empty, so the startup pass causes at most one restart per tab.

## Finding 7: Timeouts and failures are not stored, so a model that cannot be measured is retried, and evicts other models, on every startup
- **Severity:** High
- **Location:** Phase 2, "Algorithm" (120 s per probe; "A network error or abort ends the measurement with `error`"). Phase 3, `installedUnmeasured` ("no entry, or a stale one"). Plan.md, Risks ("finishes (seconds after startup)", "up to about a minute").
- **Flaw:** A cold first load of a large model on a CPU-only machine or a slow disk can take longer than 120 s. When the client aborts, Ollama keeps loading anyway. An `error` writes no entry, so the next startup lists the model as unmeasured again and runs the same failing search. Nothing records the attempt, backs off, or stops after a number of failures. With trained contexts of 256k there are up to about 5 loads per model, times every installed model, so "seconds after startup" is off by orders of magnitude on exactly the machines this feature targets.
- **Failure scenario:** A 30 GB model on a 32 GB RAM laptop: the first probe times out, the runner finishes loading anyway (30 s keep-alive), and the measurement ends in `error` while the unload races the still-pending load. On the next launch it happens again. The user sees "Measuring…" every morning, and their chat model is evicted every time.
- **Evidence:** `src/main/ollama/warm.ts:9` (`WARM_TIMEOUT_MS = 120_000` is the precedent the plan copies), `src/main/ollama/warm.ts:7` (the onboarding warm-up holds the model resident for 10 minutes, so the plan's claim "measurement replaces the warm model" only holds for the same tag).
- **Suggested fix:** Persist failed attempts (`{ lastError, attempts, lastAttemptAt }`) and skip automatic retries after one failure per fingerprint; only Measure again retries. Give the first, cold probe a timeout that scales with the model size from `/api/tags`. Treat a timeout as `error`, never as "does not fit".

## Finding 8: The measurement's late write can overwrite a cap set while it was running
- **Severity:** Medium
- **Location:** Phase 3, "Context" ("a single top-level key … read and written whole"), and the IPC table (`context-measure` "keeps an existing `userCap`").
- **Flaw:** A measurement awaits for up to minutes before it persists. If the handler reads the store at the start (to know the existing cap) and writes the whole key at the end, a `context-set-cap` in between is lost. The plan gives no read-modify-write rule. The repo already needs one for the same shared-prefs reason.
- **Failure scenario:** The user presses Measure on E4B, then lowers E4B's cap to 16k while the run is still going. The run finishes and writes the entry built from its start-time snapshot. The user's 16k is gone and the sidecar goes back to the measured max.
- **Evidence:** `src/main/ipc.ts:849-856` ("The entire read/merge/write stays synchronous in Main: concurrent windows can change different fields"). Tauri has an atomic `update` closure for this purpose (`src-tauri/src/prefs.rs:215`).
- **Suggested fix:** Persist with a synchronous read-merge-write at commit time: Electron does `get`, merge and `set` with no `await` between them, and Rust uses `prefs.update`. Merge only `fit`, and re-apply the cap rule against the cap that is stored at that moment.

## Finding 9: Per-model limits override the user's explicit `OLLAMA_CONTEXT_LENGTH`, and the UI shows a value the sidecar never sends for Modelfile `num_ctx` models
- **Severity:** Medium
- **Location:** Phase 1, "Requirements" (`perModel[id] ?? … ?? globalLimit`). Phase 4, "UI" ("Context [32k] of 64k measured").
- **Flaw:**
  1. Both shells promise that "a user-set value, inherited or from the login shell, wins". With the plan's lookup, the per-model entry wins over a user-exported `OLLAMA_CONTEXT_LENGTH=8192`, which silently breaks that contract.
  2. Discovery prefers a Modelfile `num_ctx` over the trained context, and patch 0001 then takes the minimum with the limit. The measurement builds its ladder from `model_info` trained context. For a model whose Modelfile sets `num_ctx 8192`, the row offers 64k and says "Context set to 64k", but the sidecar still sends 8192.
- **Evidence:** `src/main/sidecar.ts:380-381` and `src-tauri/src/omp/manager.rs:603-607` (the user-wins comment and the conditional set). Monorepo `packages/coding-agent/src/config/model-discovery.ts:316-320` (`extractOllamaContextWindow` returns the runtime `num_ctx` first). Patch 0001 test "prefers Ollama runtime num_ctx over training context metadata".
- **Suggested fix:** In patch 0005, use `min(perModel, userOverride)` when `OLLAMA_CONTEXT_LENGTH` came from the user. Main can forward a marker, or skip setting `PI_OLLAMA_CONTEXT_LIMITS` when the user's own value is present. Have `context-list` report the Modelfile `num_ctx` from `/api/show` `parameters` and clamp the row's ladder to it, or state in the row that the Modelfile limits it.

## Finding 10: Lowering a cap on a resumed long session sends more history than `num_ctx` on the next turn
- **Severity:** Medium
- **Location:** Phase 4, "UI" (toast "Applies from the next reply"). Plan.md, acceptance criterion 4.
- **Flaw:** omp checks compaction only after a turn ends (`checkCompaction` in the `agent_end` maintenance). The session resumes with history sized for the old window. The first prompt after a restart carries that history with the new, smaller `num_ctx`. Ollama does not reject an oversized prompt: it truncates it to fit `num_ctx`, so the turn runs on mangled context, and compaction happens only afterwards. No acceptance criterion or test covers a cap lowered below a session's current token count.
- **Failure scenario:** A 70k-token session on 128k. The user lowers the cap to 32k, and the tab restarts and resumes. The next reply is produced from roughly the last 32k tokens of a truncated prompt (the system and tool preamble may be partly lost), and only then does compaction run.
- **Evidence:** Monorepo `packages/coding-agent/src/session/agent-session.ts:4141,4278` (compaction runs only from `agent_end` maintenance). `patches/omp/0001-ollama-native-api-num-ctx.patch` (`runtimeOptions.num_ctx = contextWindow` on every request).
- **Suggested fix:** Make sure the resumed session compacts before the first prompt when its token count exceeds the new window: either a pre-prompt compaction check in patch 0005, or an explicit `compact` RPC from the GUI after the restart. Add an acceptance test for "cap lowered below the session's size".
