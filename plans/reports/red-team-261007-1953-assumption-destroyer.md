# Red team: Assumption Destroyer / Scope Auditor

Plan: `plans/261007-1948-ollama-context-fit/` (plan.md, phase-01..05). Locked user decisions (per-model limits via a new sidecar patch, full load-and-search, triggers = Measure + after pull + hardware change) are not attacked; only how they are implemented.

## Finding 1: The scheduler has no real single owner, and its streaming gate and restart fan-out only cover one window
- **Severity:** Critical
- **Location:** Phase 4, "Scheduler": "A small queue owned by the main window (not by each tab), so only one instance runs" / "restart every idle tab's sidecar"; plan.md AC 5 ("never runs while any tab is streaming")
- **Flaw:** The renderer has no idea which window is the "main" one. In main, `getMainWindow()` just returns the first live record, and every window renders the same `App.tsx`, which mounts `ProvidersWindow`. So the scheduler either runs in every window or in none. The streaming state it gates on (`useSessionStore` and per-tab `isStreaming`) is local to each renderer. `SIDECAR_RESTART` finds its target through `BrowserWindow.fromWebContents(event.sender)`, so a renderer can only restart its own window's tabs.
- **Failure scenario:** Two windows are open and window B is streaming a reply. Window A sees no streaming and starts a measurement. Ollama has to reload or evict B's model mid-reply, or B's model holds VRAM, so the stored max comes out artificially low. AC 5 fails, and the bad value is persisted. On `context-changed`, A restarts only A's tabs, so B's tabs keep the old `PI_OLLAMA_CONTEXT_LIMITS` and AC 4 fails. With N windows, N schedulers each enqueue every stale tag at startup. The main single-flight then rejects with `busy`, and the plan does not say what a scheduler does after `busy`: retry means duplicate measurements, dropping means a tag is never measured.
- **Evidence:** `src/main/window.ts:393-398` (`getMainWindow` = first non-destroyed record); `src/renderer/App.tsx:91-92,621` (every window renders ProvidersWindow); `src/main/ipc.ts:861-871` (restart scoped to the sender's window); `src/renderer/stores/tabs.ts:666-676` (streaming state is per-renderer); `src/main/ipc.ts:849-850` (the codebase already handles "concurrent windows" for prefs).
- **Suggested fix:** Move the scheduler, the streaming gate and the restart fan-out into main / Rust, where `sidecarPool` sees every tab in every window. A main-side "any sidecar running" check plus `sidecarPool` iteration replaces the renderer queue. The renderer only sends `enqueue(tag, reason)` and listens to progress.

## Finding 2: Restarting "every idle tab" through `sidecar:restart` resumes the wrong session or wakes asleep tabs, and repeats once per measured model
- **Severity:** High
- **Location:** Phase 3, "Applying a change"; Phase 4, "On `ollama:context-changed`, restart every idle tab's sidecar through the existing resume-restart IPC"
- **Flaw:** That IPC resumes only the `sessionPath` the renderer passes in. Every existing caller passes the active runtime's `sessionFile`. Background and asleep tabs often have no session runtime store in the renderer, so they have no `sessionFile`. `restart(undefined, undefined)` sets `#resumeSessionPath = null`. Once the tab has booted, `--no-auto-resume` is not added (`#freshLaunchPending` is false), so omp auto-resumes the latest session in the cwd. "Idle" also covers `asleep` tabs, which were restored but never started, so restarting them spawns sidecars the user never opened. Finally, every measurement emits `context-changed`. A startup with K stale models (see Finding 3 for why that happens spuriously) restarts every tab K times, while the user is typing.
- **Failure scenario:** Tab 2 is a background tab whose runtime was never hydrated. After a measurement it is restarted without a session path and opens tab 1's session file (the newest in the cwd), so two tabs write to one session. Meanwhile 6 restored-but-asleep tabs spawn 6 sidecars of about 120 MB each.
- **Evidence:** `src/main/sidecar.ts:697-702` (restart resets the resume path), `src/main/sidecar.ts:362` and `:573` (`--no-auto-resume` only on the first launch); `src-tauri/src/omp/manager.rs:796-797` ("later restarts may auto-resume"); `src/renderer/lib/command-registry.ts:232` and `SettingsWindow.tsx:230` (callers pass only the active runtime's `sessionFile`); `src/renderer/stores/tabs.ts:666-676` (`sessionRuntimeStore` may be absent); `src/main/sidecar-pool.ts:536-547` (`asleep` state).
- **Suggested fix:** Do the restart in main from `sidecarPool`, using each sidecar's own current session path, and skip `asleep`/`exited`/`error` entries (they pick up the env on their next start). Better still, avoid restarts: the agent already live-rebinds a model whose `contextWindow` changes after `reapplyModelPolicies()` (`packages/coding-agent/src/session/agent-session.ts:10517-10526`). If patch 0005 reads the limits from a setting (pushed through the existing `set_setting` RPC) instead of a spawn-time env var, a change applies with no restart. In either case, coalesce `context-changed` into one fan-out per scheduler drain, not one per model.

## Finding 3: The pool comes from `nvidia-smi` only, so AMD, Intel or a slow `nvidia-smi` gives a "ram" measurement that spills VRAM, and the fingerprint flaps
- **Severity:** High
- **Location:** Phase 2, "Algorithm": `pool = machine.vramBytes > 0 && !unifiedMemory ? "gpu" : "ram"`; Phase 3, `isStale`
- **Flaw:** `vramBytes` is non-null only when `nvidia-smi` answers within 2 s. On AMD (ROCm) or Intel GPUs, and whenever `nvidia-smi` is slow (a cold driver without the persistence daemon, or a busy GPU), `vramBytes` is null. The engine then uses the RAM test `size <= ramBudget`, even though Ollama is loading onto the GPU. The `isStale` field-wise compare also treats `vramBytes: 16 GiB` against `null` as a hardware change.
- **Failure scenario:** On an RX 7900 with 16 GiB VRAM and 64 GiB RAM, the RAM budget passes 128k for a dense 8B (about 18 GiB of KV). Ollama spills layers to the CPU, which is exactly the slowdown the outcome promises to prevent. On the RTX 5080 dev box, a 2.1 s `nvidia-smi` at login turns the fingerprint stale. Every model is then re-measured in the "ram" pool, and every max is raised past VRAM. The next startup, with `nvidia-smi` fast again, re-measures everything once more, which feeds Finding 2's restart storm.
- **Evidence:** `src/main/ollama/hardware.ts:9` (`HARDWARE_PROBE_TIMEOUT_MS = 2_000`), `:122-129` (VRAM only from `nvidia-smi`, `null` otherwise); `src-tauri/src/ollama/hardware.rs:250-258` (same); `src/shared/ollama-catalog.ts:108-115` (`fitOf` only means something for a catalog estimate, not for an observed load); research report, "Ollama's response for a CPU-only or AMD setup was not tested here."
- **Suggested fix:** Pick the pool from Ollama itself: if the floor probe shows `size_vram > 0`, use the GPU test (`size_vram >= size`), otherwise use the RAM test. Use the `nvidia-smi` result only for the fingerprint, and do not count a `null` VRAM reading as a hardware change when the stored value is non-null (treat it as "unknown").

## Finding 4: The measurement itself loads oversized rungs and can push the machine into swap or the OOM killer
- **Severity:** High
- **Location:** Phase 2, "Algorithm": `binary-search the largest rung` with `fits(n) = load(tag, n) then /api/ps`; plan.md "Outcome" ("can no longer push the machine into CPU spill, swap or the OOM killer")
- **Flaw:** The RAM test and the spill test run after Ollama has already allocated the rung. Binary search starts in the middle of the ladder. For a model trained at 262144 (installed here, `Quyet-1.0-Medium` reports `context_length: 262144`), the first probe is 32k–64k, and the next ones jump upward. The research report confirms that Ollama offloads instead of failing, so an oversized rung is not refused. It gets allocated in RAM.
- **Failure scenario:** A 16 GiB-RAM laptop with an 8 GiB GPU measures a dense 8B (144 KiB per token). The probe at 131072 allocates about 18 GiB of KV, mostly in system RAM. The desktop swaps hard or the OOM killer takes the browser, while the background job the scheduler started on its own ("stale" at startup) is running. On unified-memory Macs the same happens through memory pressure.
- **Evidence:** Plan Phase 2, "Algorithm" (probe, then check); research report table and the "offloads layers to the CPU instead of failing" note; `curl localhost:11434/api/tags` on this machine lists `hf.co/mradermacher/Quyet-1.0-Medium-GGUF:Q4_K_M` with `context_length: 262144`.
- **Suggested fix:** Probe the floor (and the next rung) first. Fit `size(n) = a + b·n`, which the research shows is linear, and never load a rung whose predicted `size` exceeds the pool budget plus a margin. Then binary-search only among the rungs that are predicted to fit, and keep the post-load check as confirmation.

## Finding 5: Store keys are raw tags, but pulls use bare tags and Ollama lists `:latest`, so measured models show as unmeasured and are measured again
- **Severity:** High
- **Location:** Phase 3, "IPC" (`context-measure {tag}` persists under `tag`; `installedUnmeasured` = installed tags with no entry); Phase 4, "After a pull succeeds … enqueue the tag"
- **Flaw:** Every catalog and onboarding tag is bare (`hf.co/google/gemma-4-E4B-it-qat-q4_0-gguf`), while Ollama lists it as `…-gguf:latest`. The codebase already needs a case-insensitive, prefix-aware matcher for this (`installedName`, `withDefaultTag`). The plan defines no normalization for the store. Only the sidecar lookup in Phase 1 aliases `:latest`, and only in the sidecar.
- **Failure scenario:** After onboarding, the measurement is stored under the bare tag. `context-list` compares it against the installed `…:latest`, so the row in the Ollama window shows "Not measured yet" right after a successful measurement. The next startup measures it again as "stale" and stores a second entry. The user caps `…:latest` while the bare entry keeps its own `userCap: null`, and `contextLimitsEnv` sends both keys. The sidecar's exact-match-first rule then decides which one applies, depending on which spelling discovery returns.
- **Evidence:** `src/shared/ollama-catalog.ts:45,53,61` (bare catalog tags), `:124-147` (`installedName` lowercases and matches a bare name at the `:` boundary; `withDefaultTag`); `packages/coding-agent/src/config/model-discovery.ts:569` (sidecar id = `/api/tags` `model || name`, which is `…:latest`); live `/api/tags` returns `hf.co/google/gemma-4-E4B-it-qat-q4_0-gguf:latest`.
- **Suggested fix:** Before any store read or write, resolve the tag to the name Ollama lists. Run `installedName(probe.installedTags, tag)` in main / Rust for both `context-measure` and `set-cap`, reject a tag that is not installed, and key the store by that exact listed name. Add a test that pulls a bare tag and lists `:latest`.

## Finding 6: Per-model limits silently override a user's explicit `OLLAMA_CONTEXT_LENGTH`
- **Severity:** Medium
- **Location:** Phase 1, "Requirements": `perModel[id] ?? … ?? globalLimit`; Phase 3, "Spawn env"
- **Flaw:** Today a user-set `OLLAMA_CONTEXT_LENGTH` (inherited or from the login shell) wins over the GUI default in both shells, and the research report requires that it "must stay a hard cap". With 0005, a measured value takes precedence over it. A user who set 16384 on purpose, for speed or for the small-model quality concern the plan itself names as a non-goal, now gets 131072 after the first measurement.
- **Evidence:** `src/main/sidecar.ts:375-378` ("a user-set value, inherited or from the login shell, wins"); `src-tauri/src/omp/manager.rs:604-609` (sets the default only when the user has not set it); research report, "Recommended design" item 2.
- **Suggested fix:** In the GUI, compute `min(effective, userEnvValue)` when `OLLAMA_CONTEXT_LENGTH` comes from the user's environment, or in 0005 use `min(perModel, override)` when the override is user-sourced. Show the env cap in the row, so the select does not offer values that cannot apply.

## Finding 7: "Main/Rust is the only writer" has no enforcement, and the Rust spawn path breaks the port-only module boundary
- **Severity:** Medium
- **Location:** Phase 3, "Main/Rust is the only writer of `ollamaContextFit`"; "Spawn env" (`manager.rs` reads `ctx.prefs.get("ollamaContextFit")` and needs `context_fit_store.rs` from the ollama module); "Files"
- **Flaw:** The generic `prefs:set` refuses only keys listed in `MAIN_OWNED_PREF_KEYS` (TS and Rust twins), and the plan does not add `ollamaContextFit` to either list. Any renderer code path, for example a settings import or sync, can write an unclamped `maxContext` or `userCap`. The spawn path then sends it, which defeats AC 3's clamp. On the Rust side, `omp/manager.rs` today imports only `bridge`, `ports` and `product`, and reaches other modules through `ctx` ports. Parsing the ollama-owned shape there adds a direct `omp → ollama` dependency that `cross-module-calls.json` does not list and that the files list does not mention. In the Rust measure flow, the plan also does not say whether `context-measure` re-reads `userCap` at persist time. A `set-cap` made during a 60 s measurement is lost if the entry was read at the start.
- **Evidence:** `src/main/quick-entry-shortcut-core.ts:72-80`, `src/main/ipc.ts:829-834`; `src-tauri/src/desktop/shortcut_core.rs:286-291`, `src-tauri/src/desktop/mod.rs:500-501`; `src-tauri/src/omp/manager.rs:26-31` (only bridge, ports and product imports); `src-tauri/contracts/cross-module-calls.json`.
- **Suggested fix:** Add `ollamaContextFit` to both main-owned key lists, with tests. Expose `context_limits_env()` through the ollama port, so `omp` calls a port method and the call is recorded in `cross-module-calls.json`. Either clamp again at spawn (`effective = min(userCap, maxContext)` with the parser rejecting bad shapes) or do it in the port. Persist with a read-modify-write that re-reads the entry after the measurement finishes.

## Finding 8: The `ollama-chat` cap branch is not the only path that decides `contextWindow`, so a measured max can be exceeded
- **Severity:** Medium
- **Location:** Phase 1, "Context" ("A per-model lookup here is the smallest change"); plan.md AC 3 ("never raise it past that maximum")
- **Flaw:** The cap applies only to the implicit provider (`provider === "ollama" && api === "ollama-chat"`), and that provider exists only when `models.yml` does not configure `ollama`. The GUI's own provider cleanup deliberately keeps an `ollama` entry. When it is present, discovery uses the configured api, the per-model branch never runs, and no `num_ctx` is sent at all. Separately, `#applyProviderModelOverrides` runs after `#normalizeDiscoverableModels`, so a `modelOverrides` `contextWindow` in `models.yml` replaces the capped value.
- **Failure scenario:** A user upgraded from 0.9.x with `providers.ollama` in `~/.omp/agent/models.yml`. The Ollama window shows "Context 32k of 64k measured", the sidecar ignores `PI_OLLAMA_CONTEXT_LIMITS`, and `/api/ps` shows Ollama's own default, so AC 4 fails silently. Another user has `modelOverrides` with `contextWindow: 262144`, which sends 262k past the measured 64k max.
- **Evidence:** `packages/coding-agent/src/config/model-registry.ts:1461-1468` (branch condition), `:1501` (`!configuredProviders.has("ollama")`), `:1406-1411` and `:1975-1980` (overrides applied after normalization); `src/main/provider-cleanup.ts:92` ("an `ollama` entry stays").
- **Suggested fix:** Either apply the per-model limit as the last step for every model whose provider is `ollama` (after overrides), or detect a configured `ollama` provider in the GUI and show "context limits are not applied: models.yml configures Ollama". Add a 0005 test with a `modelOverrides` `contextWindow` above the limit.
