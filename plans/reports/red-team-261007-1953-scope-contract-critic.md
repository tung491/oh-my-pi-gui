# Red team: scope and contract review of plan 261007-1948-ollama-context-fit

Perspective: Scope & Complexity Critic, plus Contract Verifier. Locked user decisions (per-model limits through patch 0005, full load-and-search, the three triggers) are not challenged.

## Finding 1: The Tauri channel registry and channel count are in the wrong place or missing, and one event is undeclared
- **Severity:** High
- **Location:** Phase 3, sections "Context", "IPC (both shells, same names)", "Applying a change" and "Files"
- **Flaw:** The plan says Tauri Ollama IPC "is registered in `src-tauri/src/ollama/ipc.rs`". Registration actually lives in `ollama/mod.rs`, in three places: the `CHANNELS` scope table, the `EMITS` list and `register()`. `ipc.rs` holds only the handler bodies. `src-tauri/tests/channels.rs` is listed only "if channels are enumerated there". It does enumerate them, and it hard-codes `EXPECTED_CHANNEL_COUNT`. The plan also emits a new event, `ollama:context-changed`, under "Applying a change" but leaves it out of the IPC table. So it never reaches `IPC_EVENTS`, `ollama::EMITS`, the bridge (`onContextChanged`) or the count. On top of that, `src/preload/index.ts` is listed for changes but needs none, because it only delegates to `createOmpApi`.
- **Failure scenario:** An implementer adds handlers to `ipc.rs` and follows the IPC table. `every_channel_has_one_owner` then fails with "channels in ipc-types.ts without a Rust owner", or `ollama:context-changed` is emitted without being declared. The count assertion fails on top of that: 4 commands plus 2 events take it from 92 to 98, not 92 to 97.
- **Evidence:** `src-tauri/src/ollama/mod.rs:31-53` (`CHANNELS`, `EMITS`, `register`); `src-tauri/tests/channels.rs:14` (`EXPECTED_CHANNEL_COUNT: usize = 92`), `:52-68`; `src/shared/ipc-types.ts:100-104` (the `IPC_EVENTS` Ollama entries); `src/shared/bridge/create-omp-api.ts:350-363`; `src/preload/index.ts:29-35`.
- **Suggested fix:** List every surface explicitly: `ipc-types.ts` (`IPC_COMMANDS` ×4, `IPC_EVENTS` ×2 including `context-changed`), the `OmpApi` type at `ipc-types.ts:1308`, `create-omp-api.ts` plus its test, `ollama/mod.rs` `CHANNELS`/`EMITS`/`register`, `ollama/ipc.rs` handlers, `channels.rs` count 98, and `ollama.api.txt`. Remove `preload/index.ts` from the list.

## Finding 2: The single scheduler in "the main window" does not exist, because every window is a main window
- **Severity:** High
- **Location:** Phase 4, section "Scheduler"; Phase 3, section "Applying a change"
- **Flaw:** The plan puts the queue in the renderer, "owned by the main window … so only one instance runs". Every BrowserWindow mounts the same `App`, and the app supports many windows. So there are N schedulers. Each one's "no tab is streaming" gate sees only its own window's tabs. The restart IPC it reuses resolves sidecars only for the calling window. Electron Ollama events go to `event.sender` only.
- **Failure scenario:** With two windows open, window A's scheduler starts a startup measurement while window B is mid-reply. The measurement unloads and reloads models at changing `num_ctx` under B's turn, so B stalls or its model is evicted. Afterwards `context-changed` reaches only A, so B's idle tabs keep the old limit until they restart for some other reason. Both windows also run the startup stale enqueue, and the second gets `busy` rejections.
- **Evidence:** `src/main/window.ts:136` (`createWindow`), `:410` (`getAllWindows`); `src/renderer/App.tsx:91,621` (`ProvidersWindow` is mounted per window); `src/main/ipc.ts:861-871` (`SIDECAR_RESTART` uses `BrowserWindow.fromWebContents(event.sender)` and only that window's pool); `src/main/ollama/register-ipc.ts:44-49` (progress goes to the sender only).
- **Suggested fix:** Run the queue and the idle gate in main, and in Rust in the `ollama` module, where `sidecarPool` sees every tab in every window. Let main restart idle sidecars directly with their session path, and defer streaming ones to their turn end. This also deletes `src/renderer/lib/context-fit-scheduler.ts`, its test and the renderer restart fan-out, so the plan gets smaller.

## Finding 3: Every measurement restarts every idle tab, including during onboarding
- **Severity:** High
- **Location:** Phase 3, section "Applying a change"; Phase 4, section "Scheduler" (startup and after-pull enqueues)
- **Flaw:** `context-changed` fires after every `context-measure` whose effective value changes. Today no model has a measurement. So after upgrading, every user's first launch measures every installed model one after another, and each measurement restarts all idle tabs: K models cause K restarts of every tab. In onboarding the order is pull, then `ollama:warm`, then measurement, which evicts the warm model. Then comes a sidecar restart, while the welcome flow is still sending `set_model` / `set_model_role` to that same sidecar.
- **Failure scenario:** A user finishes the first-run download. The automatic measurement restarts the sidecar at the moment the welcome dialog calls `set_model`. The RPC goes to a dying process, so the default model is never set, and the warm-up just paid for is thrown away.
- **Evidence:** `e2e-tauri/onboarding.e2e.ts:104-112` (it asserts that `get_available_models` with `forceRefresh`, `set_model` and `set_model_role` are recorded on the first sidecar right after the pull); `src/main/ipc.ts:871` (`sidecar.restart`).
- **Suggested fix:** Record on each sidecar the limits JSON it was spawned with. Restart only when the newly computed `PI_OLLAMA_CONTEXT_LIMITS` differs from that value, and only after the queue has drained (one restart per batch). Do not restart a sidecar while onboarding is in progress. Do not warm a model that is about to be measured.

## Finding 4: Both onboarding e2e suites break, and the plan reshapes a shared test helper
- **Severity:** High
- **Location:** Phase 2, sections "Files" (`test-fake-ollama.ts` / `.rs`) and "Algorithm" (error classes); Phase 5, section "Full gates"
- **Flaw:** The onboarding fakes in both shells answer only `/api/version`, `/api/tags`, `/api/generate` and `/api/pull`, and return 404 for everything else. The automatic measurement after a pull will call `/api/show` and `/api/ps`. The algorithm defines only HTTP 500 ("not fitting") and network or abort errors. A 404 is undefined, and a missing `/api/show` falls through to "131072, `trainedUnknown`". So an unreachable or unsupported endpoint can be stored as a real measurement (for example `max=8192`, verdict `spills`) and trigger restarts. Phase 5 lists no e2e run and no `e2e-tauri/check-twins.ts`. Separately, `test-fake-ollama.ts` is a generic server that takes an injected handler and has no routes, and both e2e suites import it. Building a VRAM simulator into it adds behaviour for every consumer.
- **Failure scenario:** `bun run test:e2e:tauri` and the Playwright `e2e/onboarding.e2e.ts` hit an unexpected restart or a stored bogus measurement after the pull. On a real user machine running an Ollama build without `context_length` in `/api/ps`, or behind a proxy, a model can be pinned at 8k for good.
- **Evidence:** `e2e-tauri/onboarding.e2e.ts:23-50` (404 fallback at line 50); `e2e/onboarding.e2e.ts` (the same fake); `src/main/ollama/test-fake-ollama.ts:15-34` (handler-only server); its consumers are `warm.test.ts`, `probe.test.ts`, `pull.test.ts` and both onboarding specs.
- **Suggested fix:** Treat any non-2xx from `/api/show` or `/api/ps`, or a missing `size`/`size_vram`, as `error`, and never persist it. Keep the VRAM simulator in the handler of `context-fit.test.ts` (and the Rust test). Add `/api/show` and `/api/ps` handlers to both onboarding fakes, or assert there that measurement is skipped. Add both e2e suites and `check-twins.ts` to the Phase 5 gates.

## Finding 5: "Main is the only writer" is claimed but not enforced, so the OOM ceiling can be bypassed
- **Severity:** High
- **Location:** Phase 3, section "IPC", last line ("the renderer never writes it through generic prefs")
- **Flaw:** `prefs:set` accepts any key except the main-owned set, and that set holds only `quickEntryShortcut` and `quickEntryTarget`. The plan adds `ollamaContextFit` to neither shell's set. `effectiveContext = min(userCap ?? max, max)` trusts the stored `fit.maxContext`. A renderer write, or any future settings code that round-trips the whole prefs object, can set `maxContext: 262144`, and the spawn env passes it through. The user's main requirement, a ceiling against OOM, then depends on renderer discipline only.
- **Failure scenario:** A generic prefs save (or a compromised renderer) writes `ollamaContextFit.models[tag].fit.maxContext = 262144`. On the next spawn the sidecar sends `num_ctx 262144`, and on a 16 GiB GPU Ollama spills to the CPU, which is the slowdown the feature exists to prevent.
- **Evidence:** `src/main/ipc.ts:829-834`; `src/main/quick-entry-shortcut-core.ts:72-79`; `src-tauri/src/desktop/shortcut_core.rs:290-291`; `src-tauri/src/services/ipc.rs:316`.
- **Suggested fix:** Add `ollamaContextFit` to `MAIN_OWNED_PREF_KEYS` in both shells, with a refusal test in each, which the parity check pairs. The `ipc.ts` and `services/ipc.rs` guards then reject renderer writes.

## Finding 6: The persisted shape and its twin parsers are gold plating
- **Severity:** Medium
- **Location:** Phase 2, section "Types"; Phase 3, section "Store shape"
- **Flaw:** The store keeps the whole `ContextFit` per model: `probes[]`, `pool`, `trainedContext`, `measuredAt` and a full `machine` object. The tolerant parser `parseContextFitStore`, its Rust twin and parity-paired tests must validate every one of those fields in two languages. `MachineFingerprint` is `MachineFacts` minus `threads`, added as a new type. `fingerprintOf` is "shared by main and the renderer", although main already returns `stale` in `context-list`, so the renderer never needs it. The probes exist only for the Phase 5 manual comparison. A log line covers that.
- **Failure scenario:** Each extra field adds a TS parser branch, a Rust parser branch, two tests with matching names and a parity entry. A drift between the two parsers (for example Rust rejecting a `probes` entry that TS accepts) drops the whole model entry in one shell only. The prefs file is shared, so the user loses a cap after switching shells.
- **Evidence:** `src/shared/ollama-types.ts:64-73` (`MachineFacts` already has these fields); `src-tauri/contracts/ollama.parity.json` (every paired TS test needs a Rust twin); `scripts/check-test-parity.ts:1-7`.
- **Suggested fix:** Persist `{ maxContext, verdict, fingerprint: Omit<MachineFacts, "threads">, userCap }` per tag. Log the probes from main instead of storing them. Keep `fingerprintOf` and `isStale` in main and Rust only.

## Finding 7: The cancel channel and the step-counted progress event go beyond the request
- **Severity:** Medium
- **Location:** Phase 2, sections "Files" and "Test matrix" (cancellation, unload after cancel); Phase 3, section "IPC" (`ollama:context-cancel`, `ollama:context-progress`); Phase 4, section "UI" (the "Measuring… 32k (2 of 4) [Cancel]" state)
- **Flaw:** The user asked for measure, adjust and cap. Cancel plus step progress adds 2 channels. Each one costs an entry in `ipc-types`, the bridge and its test, the Rust `CHANNELS`/`EMITS` lists, the count, the API snapshot, an `AbortSignal` path, two cancel tests in both languages and two UI states. A pending `context-measure` promise already gives a plain "Measuring…" state. Measurement is bounded by the probe timeout and `⌈log2 rungs⌉+1` loads.
- **Failure scenario:** Mostly cost, but there is a real defect path as well. A cancel that arrives between the `/api/generate` load and the `/api/ps` read leaves the model loaded with `keep_alive 30s` at a large `num_ctx` unless the unload in `finally` is right in both languages. That is two more race-prone code paths, for a feature nobody asked for.
- **Evidence:** `src/shared/ipc-types.ts:172-175` (the pull and pull-cancel pair being copied); `src-tauri/src/ollama/mod.rs:31-43`.
- **Suggested fix:** Remove `context-cancel` and the step counter. If progress has to stay, send one event carrying `{ tag, running: boolean }`, or keep only the pending-promise state.

## Finding 8: The Rust spawn path crosses a module boundary the plan does not account for
- **Severity:** Medium
- **Location:** Phase 3, sections "Spawn env" and "Files"
- **Flaw:** `src-tauri/src/omp/manager.rs` (module `omp`) would call `ollama::context_fit_store` (module `ollama`) to build the env. Today the `omp` module imports only foundation items (`ports`, `bridge`, `product`, `testing`). Cross-module calls are listed in `contracts/cross-module-calls.json` and must be trait methods in `ports.rs`, which a test enforces. The plan names neither file, and it does not name `omp.api.txt`. It also misses that `omp.parity.json` pairs `src/main/sidecar.test.ts` with `manager.rs`, so the new spawn-env test needs a Rust twin with the same name inside `manager.rs`. It says "a test next to `spawns_every_sidecar…`", but not that the names must match. `check-module.sh` gate 5 also requires `rename_all` on every serde type in the new store file.
- **Failure scenario:** The parity check fails on the unpaired sidecar test. Or a reviewer later rejects the direct `crate::ollama::` import from `omp`, which forces a rework of the spawn path after Phases 1–4 are already built on it.
- **Evidence:** `src-tauri/src/ports.rs:831-849` (`every_inventoried_cross_module_call_is_a_trait_method`); `src-tauri/contracts/cross-module-calls.json`; `src-tauri/contracts/omp.parity.json` (`sidecar.test.ts` ↔ `omp/manager.rs`); `src-tauri/src/omp/manager.rs:197` (it already reads prefs directly with `ctx.prefs.get`); `scripts/check-module.sh:102-108` (gate 5).
- **Suggested fix:** The `omp` side only reads a pref and turns it into a string. Keep that reader (parse, effective value, env JSON) inside `omp/` as the spawn-side consumer, and leave writing to the `ollama` module. That avoids the cross-module call. Otherwise add an `OllamaPort` trait method plus an inventory entry. List `omp.api.txt` and the `omp.parity.json` twin obligation in the plan.

## Finding 9: The tag key is not canonical on the GUI side, and the alias logic sits in the wrong place
- **Severity:** Medium
- **Location:** Phase 1, section "Requirements" (the three-way `:latest` lookup); Phase 3, section "IPC" (`installedUnmeasured`); Phase 4, section "Scheduler" (`enqueue(tag, "pulled")`)
- **Flaw:** The sidecar names models by `item.model || item.name` from `/api/tags`. The GUI probe uses `row.name`. The "pulled" trigger enqueues whatever tag the user typed (for example `gemma3` or `hf.co/x/y`, without `:latest`). The plan makes up for this inside the patch with a three-way alias lookup, which adds more patch code and more surface for upstream conflicts. On the GUI side it does not normalize at all: `installedUnmeasured` compares installed tags that end in `:latest` with stored keys that may not.
- **Failure scenario:** A user pulls `gemma3`. The measurement is stored under `gemma3`. At every startup `context-list` reports `gemma3:latest` as unmeasured, so the model is measured again (evicting it and restarting idle tabs, see Finding 3) on every launch, and the store gains a duplicate entry.
- **Evidence:** `src/main/ollama/probe.ts:123-129` (`row.name`); `../oh-my-pi/packages/coding-agent/src/config/model-discovery.ts:568-569` (`item.model || item.name`); `e2e-tauri/onboarding.e2e.ts:84` (the catalog pulls already carry `:latest`, while free-typed pulls may not).
- **Suggested fix:** In main and Rust, map the tag to its `/api/tags` name before measuring and before writing to the store, using a single helper. Then the patch needs only an exact-id lookup, plus at most one `:latest` fallback.
